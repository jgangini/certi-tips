# Initial architecture decision · 2026-09-28

CertiTips is a static site. Markdown and the course catalog enter a build script; markdown-it parses the chapters; a shared layout renders static HTML. The browser adds navigation, an accessible native diagram dialog and a quiz. A pure quiz module owns selection, confirmation, restoration and scoring. Storage failures fall back to memory. There is no backend or browser-loaded third-party runtime.

The validator checks published artifacts, editorial coverage and the question bank by responsibility in one script. Tests use Node's built-in runner. Browser smoke tests exercise the deployed paths and controls without screenshots.

## Bootstrap gate comparison

The initial Sentrux baseline was saved when the repository contained only the two architecture wrappers: quality 9952, no imports, no complex functions. It is deliberately retained, rather than overwritten to make the new application appear unchanged.

The first implementation necessarily introduces parsing, rendering, state validation and imports between source and test files. The first comparison reported lower quality/coupling scores, zero cycles and zero god files. The validator was then separated into focused validation functions to address its real reviewability problem.

For this initial release, the increase from an empty scaffold to an application is an **intentional, documented architectural tradeoff**. A DEGRADED result against the bootstrap baseline is reported as such, not as a passed gate. Acceptance also requires working behavioral tests, no dependency cycles or god files, and review of the new functions. No architecture rules are invented; `.sentrux/rules.toml` was absent, so the rule check has no configured contract to evaluate.

Future work should save its own preflight baseline against this working application. It must not use this initial-release exception to justify later regressions.

## CertiQuiz group practice · 2026-10-07

CertiQuiz stays inside the static CertiTips site at `/certi-tips/certiquiz/`, using the shared layout and assets. The dedicated `certiquiz.cloudtechnext.net` host serves only HTTPS APIs. A subdomain is not technically mandatory; a route on an existing API host would work. We retain a separate host to keep proxy configuration and host-only cookies separate from other VPS applications. The public API address is not a secret or an administrative interface.

The API owns room membership, deadlines, answer validation and scoring. It packages the existing catalog and question banks from this repository, rather than fetching arbitrary URLs or trusting a browser's answer key. FastAPI and a separate PostgreSQL instance provide durable state; bounded polling reuses ordinary HTTP. A row lock serializes updates within one room. The initial 100-player ceiling is expanded to 500 in the measured capacity revision below. The existing individual practice remains static.

Pages and the API are different sites. Production uses Secure, HttpOnly, SameSite=None, Partitioned session cookies, exact-origin CORS and JSON/custom-header/Origin checks on mutations. Authentication and room authorization remain mandatory regardless of CORS. All Pages paths under the same `jgangini.github.io` host share the browser origin; CORS cannot isolate one repository path. Browser tests on loopback verify cross-origin requests but do not establish production cross-site cookie compatibility.

The preflight baseline for this feature is quality 7387. Adding a stateful service is intentional and explicitly requested: shared live games cannot be coordinated by the static site alone. The service uses its own database, runtime role, volume and network, with no CloudTechNext credentials. Production publication and end-to-end HTTPS acceptance must be reported separately from local validation.

The CLI scanner uses `git ls-files`, so its ordinary 55-file scan omitted new untracked CertiQuiz files. Validation therefore uses an isolated temporary Git index and object directory, including the 24 new service/frontend/harness files without staging anything in the real index. The expanded comparison improves the quality signal but increases coupling 0.50 → 0.64 and complex functions 1 → 4, with zero cycles and zero god files. The gate is **DEGRADED**, despite the higher quality signal; it must not be reported as passed. There are no configured Sentrux rules.

This is an intentional, reviewed tradeoff for the new service, not an exception for unrelated regressions. The three newly resolved Python import edges connect the API, security and persistence responsibilities. The actual service dependency direction is `main → game/security/store` and `store → game/security`; it has no dependency on CloudTechNext or the static renderer. Review of the game/state projection and request validation found necessary branching at trust boundaries. The 141-line application factory includes fourteen nested routes/handlers/lifespan functions; splitting those only to reduce the aggregate complexity count would add routing indirection. Keep the validation, authorization and concurrency tests rather than removing defensive checks or hiding files from the gate. This comparison does not replace the original baseline.

## Public CertiQuiz rooms and GitHub catalog · 2026-10-07

Creating a room is now public. The same transaction creates the room, host session and presenter session, and cookies are issued only after it succeeds. A private host key is no longer needed; possession of the opaque session still controls only that host's room. PostgreSQL serializes creation capacity checks and keeps rate counters across restarts. Limits combine trusted client network, host session and global capacity; IPv6 addresses share a /64 bucket. Empty lobbies expire after fifteen minutes without extending that deadline on polling. These are application resource bounds, not volumetric DDoS protection.

The production catalog refreshes only from the fixed public GitHub repository and branch. A bounded, serialized refresh replaces the whole validated catalog after five minutes; errors preserve the last valid snapshot. Packaged banks provide startup fallback and deterministic local tests. Each room copies its selected questions at creation. No browser-provided URL, answer key or score enters this flow, and no new runtime package was added. Catalog parsing has one shared validator for packaged and remote banks.

The frontend first offers Host and Participant, then one form. Errors, reconnect status and confirmations belong to that form or room card. A failed initial load uses one centered message with the existing rocket SVG, respects reduced motion, and explains native reload instead of adding a duplicate reconnect button.

This phase saved its own baseline against the complete working CertiQuiz service (quality 7432, coupling 0.64, zero cycles/god files, four complex functions). Both architecture scans include untracked service sources using the temporary index described above; the real Git index is unchanged. The initial postflight found an additional complex function. Diagnostic scans isolated the increase to the frontend: excluding only that file from a temporary index removed the increase, while excluding the catalog did not. Those reduced scans are diagnostics, never final validation. The full-source gate remains authoritative. Catalog review also reused its existing text validator for the bank name to remove a duplicated type check without weakening input validation.

The role entry now selects its headings and descriptions from a small local data object instead of repeating nested ternaries. The final 81-file gate passes: quality 7432 → 7468, unchanged coupling 0.64, zero cycles/god files and no increased complex-function count. Graphify updated the AST graph; its optional SQL parser is unavailable, so PostgreSQL integration tests validate the schema instead.

The first update exposed a deployment harness gap: Docker's backup command could read the remaining SSH shell input. The previous API stayed live, and its moved source directory was restored before retrying. Backup and deployment subprocesses now explicitly receive `/dev/null`; the rollout check feeds Bash through standard input and simulates Docker consuming it, covering the actual transport. All three replacement/recovery scenarios pass. The subsequent update completed with a private database dump and previous release preserved; HTTPS browser acceptance verified anonymous creation, two participants, scoring and partitioned cookies.

## CertiQuiz capacity and invitation field · 2026-10-07

The room ceiling is 500 participants, with 30 questions and a minimum ten-second deadline. Join limits allow 500 participants sharing one public IP plus one retry each; creation limits remain independent. Local capacity acceptance reproduces the browser: it schedules the next poll one second after completion and defers polling while an answer is in flight. This is a 500-participant workload, not a constant 500-request-per-second target or capacity for ten simultaneous full rooms.

The API uses two Uvicorn workers under a combined two-CPU, 512 MiB quota and a 128-process/thread limit. PostgreSQL has its own two-CPU, 512 MiB quota and a 60-connection limit. Each worker reuses at most 20 connections through the official `psycopg_pool`, with a three-second wait and bounded queue, for at most 40 API connections. The pool closes on shutdown or startup failure and preserves commit/rollback and statement/lock timeouts. Uvicorn's HTTP concurrency bound is 1,024 per worker, including idle keep-alive connections. The Linux image uses `uvloop` and `httptools`, the native implementations [selected by Uvicorn when installed](https://uvicorn.dev/installation/). The [AnyIO thread limiter used by Starlette](https://starlette.dev/threadpool/) is set to 12 per worker instead of its default 40, reducing measured thread contention. These settings retain bounded database, CPU and memory use.

Session validation joins only the visitor's referenced room and retains session expiration, room expiration and the empty-lobby timeout. The indexed join avoids scanning and decoding every retained room; a local `EXPLAIN ANALYZE` comparison reduced that query from 20 rooms/98 blocks to one room/9 blocks. A room poll uses one SQL query with materialized CTEs to read database state, compare the supplied version and project the necessary fields. Changed responses contain the current question, phase metadata, counts and the caller's own player/answer during play. Lobby and results retain the player data required by their lists. This avoids transferring and decoding the complete question bank and all participants on each open-question poll.

An authorized poll with `?version=N` receives HTTP 204 only when the database version matches and no question deadline has elapsed. Membership is checked against the actual player or room owner before that response. Changed state returns HTTP 200; an elapsed deadline forces the existing transaction path to re-read complete state and the database clock after acquiring the row lock, even if the supplied version matches. Mutations retain their row lock. Partial state is never written, and PostgreSQL remains authoritative across workers and restarts, without a process-local room cache. Room GET/answer/control handlers return JSON-compatible snapshots through `JSONResponse`; cookie-issuing routes retain their response handling.

Integration checks compare full-state and projected host/player responses through two questions and every phase, and exercise concurrent deadlines, authorization, session revocation and rollback. The HTTP load check uses 500 participants, up to 30 selected questions, lobby/reveal polling, two ten-second rounds and answer waves bounded at 64. The default browser mode requires poll/answer p95 at most one second, every request below ten seconds, poll start-gap p95 at most two seconds and delivery of each question to every participant within two seconds. Busy deferrals remain included in the gap measurement. One participant remains unanswered to exercise the deadline; a separate integration check verifies 500 accepted and scored answers.

The local browser-mode run passed with 13,815 requests and no errors. Its 12,296 polls had p95 461 ms and maximum 608 ms; 998 answers had p95 649 ms and maximum 879 ms. All 500 participants received both questions within 1,042/1,036 ms, and the answer waves completed in 5,592/5,539 ms. Observed polling throughput was 427.95 requests/second, with start-gap p95 1,494 ms and maximum 2,539 ms including busy deferrals. The local artifact is `output/certiquiz-500-browser-mode-load.json`. The retained `--poll-mode=fixed` stress mode targets fixed start-to-start cadence; its measured run failed with 25 late answers and answer p95 1,148 ms. That failure remains a capacity boundary, not a passed result. No 500-participant VPS load was performed.

Final validation for this phase passed 47 service tests using an isolated PostgreSQL profile and the full 81-file architecture gate: quality 7468 → 7470, unchanged coupling 0.64, zero cycles and zero god files. Sentrux reported no degradation. Graphify updated its AST graph to 776 nodes and 1,179 edges; its optional SQL parser remains unavailable, so the PostgreSQL integration suite validates the SQL behavior. No new architecture rules were introduced.

The invitation control reuses native read-only input and button elements, with the copy icon integrated at the right and feedback inside the room card. The large lobby PIN is retained and the redundant header badge removed. Form focus uses the site's blue accessibility outline. No frontend dependency or database schema migration was added.
