## Active Sentrux contract · 2026-10-08

`.sentrux/rules.toml` now defines the project contract; historical statements below about missing rules describe earlier revisions. The current source has no import cycles or god files, so both are prohibited. The five subsystem boundaries keep browser assets, site tools and the CertiQuiz API independent: the browser uses HTTP for live rooms, the server consumes catalog data, and deployment/verification tools use commands or HTTP rather than importing API implementation code.

The dependency direction is tests → application/tools → adapters/rendering → domain/security. `quiz-core.js` and the server's `game.py` / `security.py` cannot depend on UI, storage or HTTP handlers. `storage.js`, `layout.mjs`, `store.py` and `catalog.py` provide adapters; entry points assemble them. Test-to-source imports are allowed; production-to-test imports are rejected. Specific file matches precede directory fallbacks, so new source files are covered as application code until explicitly assigned a more foundational role.

Sentrux **0.5.7** rejects a larger layer order importing a smaller one. The contract therefore assigns tests `0`, entry points `10`, adapters `20` and domain/security `30`. This was verified with allowed and forbidden imports, because the [upstream README example](https://github.com/sentrux/sentrux#rules-engine) describes the opposite order. Re-run `pwsh -File scripts/check-architecture-rules.ps1` after upgrading Sentrux; it exercises the installed binary in temporary directories and checks both successful dependencies and actual cycle, layer and boundary violations without changing the real Git index.

Function-size, complexity and coupling regressions remain governed by `sentrux gate` against the working application's preflight baseline. This change does not impose arbitrary global thresholds or waive existing regressions. Rules operate on resolved static imports; they do not validate dynamic imports, HTTP behavior, browser globals, authentication or CORS. Sentrux's normal Git scan covers tracked files: new source must also be included in architecture acceptance (an isolated temporary index can do this without staging user changes). Generated artifacts and the local baseline stay ignored; only `rules.toml` is eligible for version control.

The installed Python plugin v0.2.0 only captures `dotted_name` imports in `queries/tags.scm`; an isolated probe confirmed that `from .store import Store` produces no import edge. The Python rules therefore apply to resolved absolute imports, but do **not** establish enforcement of the API's existing relative imports. The regression script requires resolved edges in every case and tests supported absolute imports explicitly. Fixing/upgrading that external parser and rechecking relative imports is needed before claiming full Python dependency coverage; no production imports were rewritten to accommodate the analyzer.

The existing preflight/postflight wrappers already run `sentrux check .`, so this contract is enforced without adding a deployment or CI workflow. Run `sentrux check .` for all eight checks, `sentrux gate .` for regression comparison, and `scripts/arch-postflight.ps1` for the combined Graphify/check/gate workflow. The installed MCP `check_rules` response is limited to three checks; the CLI is required for full configured-rule acceptance.

## CertiQuiz capacity and invitation field · 2026-10-07

The room ceiling is 500 participants, with 30 questions and a minimum ten-second deadline. Join limits allow 500 participants sharing one public IP plus one retry each; creation limits remain independent. Local capacity acceptance reproduces the browser: it schedules the next poll one second after completion and defers polling while an answer is in flight. This is a 500-participant workload, not a constant 500-request-per-second target or capacity for ten simultaneous full rooms.

The API uses two Uvicorn workers under a combined two-CPU, 512 MiB quota and a 128-process/thread limit. PostgreSQL has its own two-CPU, 512 MiB quota and a 60-connection limit. Each worker reuses at most 20 connections through the official `psycopg_pool`, with a three-second wait and bounded queue, for at most 40 API connections. The pool closes on shutdown or startup failure and preserves commit/rollback and statement/lock timeouts. Uvicorn's HTTP concurrency bound is 1,024 per worker, including idle keep-alive connections. The Linux image uses `uvloop` and `httptools`, the native implementations [selected by Uvicorn when installed](https://uvicorn.dev/installation/). The [AnyIO thread limiter used by Starlette](https://starlette.dev/threadpool/) is set to 12 per worker instead of its default 40, reducing measured thread contention. These settings retain bounded database, CPU and memory use.

Session validation joins only the visitor's referenced room and retains session expiration, room expiration and the empty-lobby timeout. The indexed join avoids scanning and decoding every retained room; a local `EXPLAIN ANALYZE` comparison reduced that query from 20 rooms/98 blocks to one room/9 blocks. A room poll uses one SQL query with materialized CTEs to read database state, compare the supplied version and project the necessary fields. Changed responses contain the current question, phase metadata, counts and the caller's own player/answer during play. Lobby and results retain the player data required by their lists. This avoids transferring and decoding the complete question bank and all participants on each open-question poll.

An authorized poll with `?version=N` receives HTTP 204 only when the database version matches and no question deadline has elapsed. Membership is checked against the actual player or room owner before that response. Changed state returns HTTP 200; an elapsed deadline forces the existing transaction path to re-read complete state and the database clock after acquiring the row lock, even if the supplied version matches. Mutations retain their row lock. Partial state is never written, and PostgreSQL remains authoritative across workers and restarts, without a process-local room cache. Room GET/answer/control handlers return JSON-compatible snapshots through `JSONResponse`; cookie-issuing routes retain their response handling.

Integration checks compare full-state and projected host/player responses through two questions and every phase, and exercise concurrent deadlines, authorization, session revocation and rollback. The HTTP load check uses 500 participants, up to 30 selected questions, lobby/reveal polling, two ten-second rounds and answer waves bounded at 64. The default browser mode requires poll/answer p95 at most one second, every request below ten seconds, poll start-gap p95 at most two seconds and delivery of each question to every participant within two seconds. Busy deferrals remain included in the gap measurement. One participant remains unanswered to exercise the deadline; a separate integration check verifies 500 accepted and scored answers.

The local browser-mode run passed with 13,815 requests and no errors. Its 12,296 polls had p95 461 ms and maximum 608 ms; 998 answers had p95 649 ms and maximum 879 ms. All 500 participants received both questions within 1,042/1,036 ms, and the answer waves completed in 5,592/5,539 ms. Observed polling throughput was 427.95 requests/second, with start-gap p95 1,494 ms and maximum 2,539 ms including busy deferrals. The local artifact is `output/certiquiz-500-browser-mode-load.json`. The retained `--poll-mode=fixed` stress mode targets fixed start-to-start cadence; its measured run failed with 25 late answers and answer p95 1,148 ms. That failure remains a capacity boundary, not a passed result. No 500-participant VPS load was performed.

Final validation for this phase passed 47 service tests using an isolated PostgreSQL profile and the full 81-file architecture gate: quality 7468 → 7470, unchanged coupling 0.64, zero cycles and zero god files. Sentrux reported no degradation. Graphify updated its AST graph to 776 nodes and 1,179 edges; its optional SQL parser remains unavailable, so the PostgreSQL integration suite validates the SQL behavior. No new architecture rules were introduced.

The invitation control reuses native read-only input and button elements, with the copy icon integrated at the right and feedback inside the room card. The large lobby PIN is retained and the redundant header badge removed. Form focus uses the site's blue accessibility outline. No frontend dependency or database schema migration was added.
